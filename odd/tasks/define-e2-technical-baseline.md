# Define the E2 Technical Baseline

## Intent

Define the smallest testable technical architecture and executable contracts required to build and close E2. The baseline must turn the product contract into stable Module Interfaces, observable behavior, failure attribution, and a verification strategy without copying or claiming a runtime implementation.

## Decisions already made

- E2 closes as a completed evidence-producing experiment, not at runtime readiness or dialing alone.
- AugloE2 is the sole implementation authority during separation.
- Sensitive evidence remains outside Git in controlled storage.
- Product chronology is append-only and distinct from mutable state and Git history.
- Specs define observable contracts; ADRs explain hard-to-reverse trade-offs only.
- The primary agent-behavior result uses exactly 20 completed/evaluable real outbound conversations under one arm and one Behavior Hash, dialed serially.
- Config Snapshots are immutable, schema-versioned, provider-neutral compositions of typed Module configuration fragments populated with resolved values by future Adapters.
- Snapshot Digest establishes exact identity and integrity over the complete canonical Config Snapshot; Behavior Hash establishes experimental comparability over the schema's versioned behavior-affecting projection.
- Every Config Snapshot field has an explicit semantic class such as behavior, provenance, operational, or secret reference. Attempt inputs and observations are excluded.
- Provenance or operational metadata may change Snapshot Digest without changing Behavior Hash. Behavior-affecting configuration changes Behavior Hash and requires a new cohort.
- Cross-schema comparison reports `full`, `partial`, or `incomparable` and never invents unknown historical behavior values.
- Historical Config Snapshots are never rewritten. A proven historical fact may be added only through a separate evidence-backed enrichment attestation linked to the original Snapshot Digest.
- The first-stack selection strategy and exactly two architecture candidate identities are resolved, while the executable qualification matrix, exact provider-neutral pass/fail evidence, winning stack, per-Adapter deployment choices, and exact real-cohort capability set remain unresolved; no provider is selected.
- Regional data residency is not a baseline entry requirement for the first real 20-conversation cohort. Existing consent, access, retention, and provider-control contracts remain authoritative.
- The selected architecture shape is a provider-neutral modular monolith: one process-level agent graph with small Interfaces and interchangeable Adapters for transport, STT, turn detection, LLM, TTS, appointment, evidence storage, and model-assisted review. This shape selects no provider.
- The official E2 pair is `controlled_cascade` and `audio_native_half_cascade`. Controlled cascade means explicit STT -> tool-capable reasoning -> deterministic pre-TTS policy/output control -> selected TTS. Audio-native half-cascade means audio-native understanding/reasoning producing controlled text/tool output -> the same deterministic pre-TTS policy/output control -> selected external/cloned TTS. These are conceptual architectures and select no provider or implementation.
- Both candidates use the same versioned replay corpus, mandatory readiness suite, canonical evidence requirements, controlled fixtures, and authorized real-telephony smoke conditions when needed.
- Managed versus selectively self-hosted deployment is an independent per-Adapter dimension available to both candidates, not a candidate identity. No Adapter deployment choice, including which Adapters might be self-hosted, is selected yet.
- Pure or full-duplex end-to-end speech-to-speech remains outside the official pair until separately qualified for exact compliant opening or required scripted speech, deterministic pre-audio policy enforcement, tool correctness and idempotency, auditability and evidence, voice rights and access, interruption behavior, and the same Pre-Run Behavioral Readiness contract.
- The bakeoff evaluates accepted hard latency gates, 20-behavior readiness results, observable conversational quality, evidence completeness, failure behavior, deterministic guardrail enforcement, estimated cost, and solo-founder operational burden. It optimizes for E2 contract compliance and operability rather than globally optimal future architecture.
- Exactly one winning stack, exact capability set, Config Snapshot, Behavior Hash, Adapter/model/voice identities, and suite version must be selected and frozen before the first admitted real Dialing Attempt. Candidate stacks cannot be mixed inside the 20-conversation cohort, and pre-cohort candidate changes do not count toward the cohort.
- Production multi-tenancy, broad on-prem deployment, Kubernetes/autoscaling, full self-hosting, and finetuning are deferred unless required to make a candidate pass E2.
- Current provider facts require fresh primary-source research, so no vendor or provider is selected yet.
- Vendor-neutral contracts remain authoritative for configuration, trace/event identity, Attempt Evidence references, outcomes, and correlation. Provider-specific trace IDs exist only in Adapter mappings.
- A production observability platform such as LangSmith is only a possible future Adapter, not a selected dependency or source of domain truth.
- Controlled Storage remains authoritative for sensitive evidence; an observability Adapter cannot silently become evidence authority.
- Every admitted Dialing Attempt owns one append-only Canonical Event Stream and one Attempt Evidence Manifest.
- Canonical lifecycle and observable-behavior events are stable provider-neutral domain contracts. Detailed runtime or provider traces are optional Adapter extensions and are never required to interpret the experiment.
- Canonical event envelopes carry stable internal event and attempt IDs, schema version, ordered sequence, occurred-at time, event type, non-sensitive payload or stable payload reference/hash, and correlation or causation references when applicable. Provider trace IDs remain Adapter mappings.
- The Attempt Evidence Manifest binds the attempt, Config Snapshot identities, canonical stream identity, artifact references and hashes, outcome, threshold proof, evaluable label and timestamp, Failure Attribution when applicable, optional Detailed Trace references, and Evidence Completeness.
- Evidence Completeness is path-sensitive and is either `complete` or `incomplete`. Incomplete evidence names missing or invalid requirements, remains visible in the Operational Attempt Ledger, and cannot be represented as a successful or complete attempt.
- Evidence-capture failure must preserve the strongest possible Operational Attempt Ledger record and Failure Attribution; a complete manifest is not assumed possible on every runtime path.
- Audio, transcripts, sensitive payloads, and provider-native traces remain in Controlled Storage. Git and canonical manifests contain only stable IDs, hashes, and non-sensitive metadata.
- The exactly 20-conversation E2 cohort is intended to remain a permanent internal benchmark for future architecture and capability branches against its frozen Behavior Hash and evidence.
- Raw benchmark audio and transcripts may be retained indefinitely only when every participant's explicit, recorded consent specifically covers indefinite retention and reuse for internal architecture and capability evaluation. A call without that consent cannot enter the permanent raw benchmark; ordinary legal and evidence handling remains separate, and this contract defines no fallback retention horizon.
- Raw benchmark evidence remains encrypted in Controlled Storage outside Git. Git and canonical manifests contain only stable references, hashes, and non-sensitive metadata.
- Benchmark access is least-privilege, purpose-bound, and auditable. The founder is the accountable E2 access authority, and every human, service, or model access records actor identity, purpose, evidence scope, and timestamp.
- Raw evidence may be sent to an external model or provider only through a selected Adapter after contractual and technical controls preventing provider retention, training, or unrelated reuse are verified.
- Future architecture branches consume immutable referenced copies or views and cannot alter original benchmark evidence. Derived artifacts identify their source evidence, transformation, tool or model and version, and output hash.
- Valid participant revocation or governing legal requirements cause deletion or restriction of affected raw evidence plus an append-only Evidence Retention Attestation. Historical Closure Candidates and original DR-5 truth remain unchanged as-of their original evidence, while future benchmark availability and completeness expose the change.
- Non-sensitive hashes, manifests, labels, decisions, and attestations are preserved indefinitely unless governing law forbids their preservation.
- Applicable legal and consent language must be validated before live calls; this product contract does not claim legal sufficiency.
- The retention contract selects no storage vendor, encryption implementation, IAM product, or model provider.
- The evidence architecture remains a T4 candidate; no ADR, observability provider, storage implementation, serialization technology, or exact stack has been selected.
- Outcome and Failure Attribution are separate: Outcome records what happened, while Failure Attribution records where and why an unsuccessful or incomplete attempt failed.
- Failure Attribution is provider-neutral, hierarchical, and multi-axis. A resolved attribution has exactly one primary attribution and zero or more contributing factors; each records lifecycle stage, causal category, responsibility, retryability/remediation class, confidence, and supporting Attempt Evidence references.
- Canonical lifecycle stages cover admission, configuration, dialing, transport/media, speech input, turn management, reasoning, tool execution, policy/guardrail, speech output, evidence capture, labeling, and experiment closure. The legacy six-value UI enum is not canonical.
- Stable causal-category families cover unavailable dependencies, timeouts, invalid input or configuration, contract violations, incorrect behavior, policy rejection, unavailable business data, missing or invalid evidence, human/environmental conditions, and unresolved pending investigation without selecting implementations.
- Responsibility distinguishes conversational agent, infrastructure, external provider, experiment operation, human/environment, shared, and unresolved.
- Retryability/remediation distinguishes a new attempt without behavior change, operational intervention, behavior or configuration change requiring a new Behavior Hash/cohort, non-retryable failure, and unresolved status.
- Attribution confidence is `confirmed`, `supported`, `suspected`, or `unknown`; only evidence-backed attribution may be `confirmed` or `supported`.
- An unresolved cause is allowed provisionally and preserves evidence, candidate causes, and investigation status without inventing a best-fit primary cause. It blocks E2 closure by default.
- DR-5 may explicitly accept unresolved attribution only by referencing the unresolved attribution and evidence, recording rationale and risk, and exposing the exception in the closure report. Acceptance does not rewrite the attribution as resolved.
- Attribution corrections are append-only revisions linked by supersession and never rewrite historical attribution evidence.
- Each admitted Dialing Attempt receives a valid founder-confirmed Outcome Label within 48 hours of its Canonical Terminal Event; the deadline is per attempt and is not measured from cohort completion.
- Outcome Label corrections are append-only revisions linked by supersession; prior labels and their evidence remain available.
- The 48-hour requirement is evaluated against the first valid founder-confirmed Outcome Label. A later correction neither cures an originally late label nor makes an originally timely label late.
- Each unsuccessful or incomplete attempt receives initial Failure Attribution triage within the same 48-hour window. When evidence is insufficient, timely unresolved triage preserves evidence references, candidate causes, investigation status, reviewer or actor identity reference, and triage timestamp.
- Timely unresolved triage satisfies the initial-triage deadline but not final attribution for closure. Root-cause resolution has no fixed 48-hour SLA and remains required before E2 closure unless DR-5 explicitly accepts and exposes the documented uncertainty under the existing exception policy.
- The E2 audit operating model is resolved for the first milestone: deterministic checks validate deadlines, event ordering, evidence completeness, threshold proof, and contract consistency before model review.
- Models may pre-label, classify, score confidence, identify evidence, and propose Failure Attribution, including reasoning-capable analysis for ambiguous causes and a possible structured probabilistic pre-labeling pilot. Every recommendation is non-authoritative and records model or Adapter identity, model or behavior version, decision schema version, available probabilities or confidence, evidence references, and generation timestamp.
- The founder reviews and confirms every admitted Dialing Attempt, including all 20 evaluable conversations and every admitted non-evaluable attempt, and is the sole human authority for initial Outcome labels and initial Failure Attribution triage.
- An independent automated pre-closure audit may advise on missing evidence and contract inconsistencies in the frozen candidate, but it is not a human approver and cannot authorize DR-5. The founder remains solely accountable for corrections, unresolved-cause exceptions, and DR-5.
- Automation may increase only after measuring agreement against founder-confirmed E2 labels and attributions. No future production threshold, model, or provider is selected; Jev and LangSmith remain nonbinding examples of interchangeable Adapters, and structured probabilistic decision models are only a candidate Adapter class.
- Before closure review, E2 produces an immutable, digest-identified Closure Candidate binding the Primary Evaluation Cohort, Operational Attempt Ledger, Attempt Evidence Manifests, current effective Outcome Labels and Failure Attributions, exceptions, and contract-check results.
- Any material post-freeze change invalidates the Closure Candidate and requires a newly frozen candidate plus the applicable contract checks and audit before DR-5.
- DR-5 binds exactly one frozen Closure Candidate.
- Post-DR-5 corrections are append-only Closure Amendments and never rewrite the historical closure or original DR-5 decision.
- A Closure Amendment affecting the experiment result, Primary Evaluation Cohort membership, Evidence Completeness, an unresolved-attribution exception, or any closure predicate requires an explicit superseding DR-5 decision. Historical closure remains true only as of its original frozen Closure Candidate.
- Founder authority remains the sole human authority across Outcome Label revisions, Closure Candidate review, Closure Amendments, unresolved-cause exceptions, and DR-5.
- The founder selected three provider-neutral hard E2 latency closure gates: end-to-end latency P50 <= 900 ms, end-to-end latency P95 <= 1800 ms, and end-of-turn latency P95 <= 1200 ms. E2 closure requires all three to pass; they are not reporting-only comparators or production targets.
- The latency gates retain the legacy provenance warning: the legacy source treated them as aspirational E2 targets, did not implement threshold enforcement, and did not directly expose aggregate end-of-turn P95 in its call-level ledger.
- The hard latency gates use per-turn measurements pooled across all metric-specific eligible turns in exactly 20 evaluable conversations. Nearest-rank percentiles over each metric's pooled population control the gates; required per-conversation distributions are diagnostic and do not control the gates.
- All canonical latency measurements use a monotonic clock. End-of-turn latency starts at the end of the last inbound audio sample classified as live-human speech and ends at the canonical end-of-turn decision. End-to-end latency starts at the same inbound-speech boundary and ends at the first outbound agent audio sample delivered as audible output.
- End-of-turn eligibility includes every completed live-human speech turn after the Evaluation Entry Threshold. End-to-end eligibility includes every such turn where the behavioral or policy contract required an audible agent response.
- If an audible response was required and the agent fails before delivering audio, the required end-to-end measurement is missing and the latency gate fails; the turn is never silently excluded.
- End-to-end exclusions are closed to two cases: the remote human disconnected before response delivery, or an applicable policy required silence or termination rather than audible output. Every exclusion requires its canonical reason code, a supporting evidence reference, and inclusion in closure reporting.
- Interruptions remain included when a response obligation existed. Eligibility and exclusion cannot be decided from the observed latency value or whether agent audio happened to succeed.
- A required missing or invalid latency measurement fails the relevant gate and is never silently excluded or imputed.
- Pooling weights longer conversations more heavily. Required per-conversation reporting mitigates but does not eliminate this bias.
- Elapsed conversation time uses a monotonic clock and begins at connection establishment for a live call, without selecting a provider or runtime implementation.
- At 240 elapsed seconds, the conversation enters a graceful-closure window. The 240-second trigger is behavior-affecting configuration, is frozen in the Config Snapshot, and is included in the Behavior Hash.
- During 240–300 elapsed seconds, the agent must pursue a natural close and must not initiate new substantive work. It may finish the in-flight atomic interaction needed to close safely, such as confirming already-collected appointment facts, but must not expand scope.
- At 300 elapsed seconds, the system must forcibly terminate the call. Forced termination is an auditable Outcome and must receive an Outcome Label and Failure Attribution when applicable.
- Any Dialing Attempt whose connected conversation exceeds 300 elapsed seconds is a hard guardrail violation and blocks E2 closure.
- Required call-duration evidence includes timestamps or events proving connection establishment, the 240-second transition, compliant closure-window behavior, and the terminal cutoff or termination.
- Before the first admitted real Dialing Attempt, the exact frozen Behavior Hash must pass a versioned, provider-neutral Pre-Run Behavioral Readiness Suite.
- Every mandatory readiness scenario must pass. An aggregate percentage cannot substitute for a failed mandatory scenario, and the legacy `offline_pass_rate >= 0.95` is not adopted.
- Legal behavior, safety behavior, evidence production, and 240–300-second graceful-closure and forced-termination scenarios are mandatory with zero tolerance. Diagnostic scenarios may fail without blocking readiness, but their results must be preserved and reported.
- Every readiness scenario has a stable ID and version, declared behavior or contract coverage, deterministic inputs or controlled fixtures, expected observable result, evidence references, and a pass/fail result.
- Each readiness result binds the suite version, exact Behavior Hash, timestamp, runner identity and version, and evidence digest.
- A behavior-affecting configuration change creates a new Behavior Hash, invalidates prior readiness for the new cohort, and requires all mandatory scenarios to be rerun.
- Every Pre-Run Behavioral Readiness Suite must include a provider-neutral simulated appointment protocol covering open day negotiation, availability query, explicit day/time confirmation before write, a simulated appointment write bound to a stable idempotency key, authoritative reread, no booked claim when write/reread fails or availability is unavailable, truthful failure behavior, and same-turn goodbye/termination after verified success. Repeating the same logical booking request with the same idempotency key must create no duplicate appointment and must return or refer to the same authoritative appointment identity with a consistent result; a different logical booking request must use a different idempotency key. This simulation is mandatory regardless of provider.
- A live Adapter canary is additionally mandatory only when the exact Behavior Hash for the real cohort advertises real appointment booking. Before the first admitted real Dialing Attempt, it must bind the cohort's exact Adapter and configuration, complete successfully, preserve evidence, verify a live appointment write bound to a stable idempotency key under the same replay and distinct-request key contract, verify authoritative reread/propagation, and verify cleanup or designated test-record handling.
- The live canary is separately authorized operational activity. It must not create or alter real business or customer records without explicit authorization and a designated test target.
- When the exact Behavior Hash does not advertise real booking, no live calendar or provider canary is required and field conversations must not claim booking capability.
- The readiness gate selects no provider, runtime, or test framework.
- The founder-approved initial mandatory readiness baseline contains exactly 20 canonical behaviors without legacy numeric IDs: Legal Dial Eligibility; Compliant Opening; Truthful AI Identity; Wrong Recipient Protection; Immediate Durable DNC; Emergency Safe Exit; Grounded Claims; Behavior Evidence Completeness; Voicemail or IVR Exit; Single Language Recovery Then Exit; Interruption Reorientation; Conversation Memory and Correction; Partial Capture Integrity; Disinterest Without Pursuit; Contextual Human Handoff; Truthful Appointment Negotiation; Verified Idempotent Appointment Commit; Same-Turn Appointment Closure; Bounded Session Termination; and No-Progress Termination.
- Every canonical behavior has at least one mandatory versioned scenario, and every mandatory scenario must pass under the readiness contract.
- Deterministic assertions own tool calls, state transitions, provenance, receipts, clocks, idempotency, and termination. Model or human judgment may evaluate semantic adequacy only and cannot override a failed deterministic assertion.
- The 20-behavior inventory is an initial versioned product baseline and does not select the final agent stack or capability set.
- Before the real cohort's exact stack and capability set are frozen, the founder may explicitly revise the inventory only through an append-only versioned revision with rationale and a coverage diff; silent edits are forbidden.
- Once the suite version, Config Snapshot, Behavior Hash, real cohort stack, and capability set are frozen, a behavior-affecting coverage or configuration change invalidates readiness, requires a new suite version and Behavior Hash, requires a new cohort when the existing Behavior Hash contract dictates, and requires all mandatory scenarios to be rerun.
- Capability coverage is resolved for the current initial baseline but remains explicitly revisable before freeze. The stack, provider, runtime, and exact real-cohort capability set remain unselected.
- AugloE2 experiment-lifecycle C1–C10 remain separate from readiness conversational-behavior names; legacy identifiers must not be copied by number into the readiness suite.
- NFR adoption is complete because the task's named blockers—latency, call duration, pre-run readiness, and benchmark evidence retention/access—are now resolved; no additional named NFR blocker remains.
- The latency, call-duration, and pre-run readiness policies select no provider, runtime stack, telemetry vendor, test framework, or implementation and do not warrant an ADR.
- The failure model selects no vendor, runtime stack, storage, or serialization, and does not yet warrant an ADR.
- Infrastructure stability is secondary to conversational-agent behavior in the primary experiment result.
- Every admitted Dialing Attempt remains in the Operational Attempt Ledger with evidence, outcome, and Failure Attribution when applicable, including pre-conversation infrastructure failures, no-answer attempts, and other non-evaluable attempts.
- Non-evaluable attempts are reported separately, excluded from the 20-conversation primary denominator, and used to drive infrastructure iteration.
- A Dialing Attempt crosses the Evaluation Entry Threshold irrevocably after the legal opening has been delivered and the system captures the first intelligible utterance from a live human; later agent or infrastructure failure cannot remove it from the Primary Evaluation Cohort.
- A live wrong-contact response crosses the threshold because wrong-contact handling is conversational-agent behavior. Voicemail, IVR, ambient noise, silence/no-answer, and unintelligible audio do not cross it and remain only in the Operational Attempt Ledger.
- Attempt Evidence must prove whether the Evaluation Entry Threshold was crossed; the full evidence schema remains unresolved.
- Selecting completed/evaluable conversations creates selection bias. Complete operational-attempt accounting mitigates that trade-off by exposing excluded outcomes, but does not eliminate it.
